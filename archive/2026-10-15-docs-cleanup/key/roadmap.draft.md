# 算子自动优化与 Profiling 工作计划（讨论稿）

更新：2026-09-27。用途：自己梳理工作，并安排组内近期任务。

本文区分材料中已明确的要求、当前已有能力和建议安排。未确定的负责人、平台、算子及日期不代填。原始讨论记录保留在 `roadmap.md`。

## 1. 要完成什么

这项工作需要同时满足两方面要求：

- **基金交付**：在国产 AI 芯片上完成 Profiling 工具和 Triton-TLE 算子优化，达到任务书要求。
- **研究所建设**：在 XSAI 上建立系统的性能采集与分析工具，让 Agent 能根据性能信息修改算子，首先提高 XSAI-BLAS 的性能。

两方面共同研究的问题是：硬件需要提供哪些信息，这些信息如何帮助判断算子慢在哪里，以及如何帮助 Agent 选对修改方法。

### 1.2 XSAI 上要形成的能力

1. 移植 cuda-optimized-skills 的工作流程，形成暂称为 XSAI-KernelAgent 的实现。
2. 从简单 C/C++ 算子开始，让 Agent 能修改代码、编译、验证结果、读取性能信息，再决定下一次修改。
3. 用实际遇到的问题决定 XSAI-prof 和 XSAI-analyzer 先做什么。
4. 将工具用于 XSAI-BLAS 中选定的算子，比较修改前后的性能。
5. 随后扩展到 Triton/Triton-TLE。

**上述先后顺序适用于 XSAI。国产芯片的设备准备、工具接入、Triton-TLE 算子选择和优化应同时推进，不能全部等待 XSAI 完成。**

## 2. 当前已有条件

| 对象 | 当前情况 | 下一步需要补什么 |
| --- | --- | --- |
| XSAI 性能信息 | 已有 XiangShan 通用 CPU 核的大量性能计数器，以及少量新添加的计数器 | 清点每个计数器覆盖的硬件部件、单位、采集窗口和解释方式 |
| XSAI emu | 按 `XSAI-emu-guide.md`，现有预编译程序是基于 Verilator 的 RTL 仿真程序，支持计数器、ChiselDB、PerfCCT 等 | 用一个实际算子检查可用数据，确认矩阵单元等目标部件的信息覆盖程度 |
| XSAI-BLAS | 已有面向 XSAI 的算子库；此前通过 NEMU 验证正确性、RTL 仿真测性能，使用 element/cycle 等指标 | 保存当前实现和测试条件，选定首批待优化算子 |
| XSAI-prof / analyzer | 有零散采集与分析手段，尚无满足上述需求的完整工具 | 把已有能力整理为可调用、可解释的输出，再补缺失信息 |
| XSAI-KernelAgent | 移植是近期任务，具体完成程度待盘点 | 确认可复用模块和 XSAI 需要替换的运行、编译与分析接口 |
| Triton/Triton-TLE 与复现工作 | 当前完成程度尚未逐项确认 | 分别记录“未开始／正在做／已有结果”及对应代码、报告 |

这里的 emu 本身就是 RTL 仿真程序，因此不把工作写成“先 RTL 仿真、后 emu”。应区分的是：当前采集了哪些信息，后续准备多采集什么，以及 Agent 实际能看到什么。

## 3. 近期先做什么

以下是建议的工作顺序，不是已经承诺的日期。XSAI 开发与国产芯片交付分别记录进度。

### 3.1 XSAI：先完成一个简单算子的自动优化

**要做的事**

- 选一个能快速编译、验证和仿真的 C/C++ 算子，保存当前代码、输入和性能。
- 移植 cuda-optimized-skills 的必要流程，适配 XSAI 编译、程序运行、正确性检查和性能读取。
- 第一版允许只读取已有计数器和日志，不等待完整 XSAI-prof。
- 保存每轮的代码、编译结果、正确性结果、性能数据、Agent 判断与修改理由。

**完成时应能拿出的东西**：可重复运行的脚本，以及一次完整优化尝试的记录，包括未提升或失败的尝试。先确认流程能运行，再判断性能是否提升。

### 3.2 XSAI：根据实际问题开发 prof 和 analyzer

**要做的事**

- 列出当前算子优化过程中无法回答的问题，例如“慢在什么代码段”“等待发生在哪个环节”。这些是待验证的问题示例，不预设已有工具能直接回答。
- 先检查已有计数器、ChiselDB 和 PerfCCT 能否回答，再决定是否增加采集点或性能计数器。
- 将性能数据与算子运行区间、PC、反汇编或源码位置关联；无法关联的地方明确标注。
- 选定 XSAI-BLAS 算子，比较旧实现与修改后的结果，解释性能变化。

**完成时应能拿出的东西**：第一版 XSAI-prof / analyzer、支持的指标清单，以及从性能信息到代码修改和测量结果的案例。数值提升目标待取得当前结果后确定。

### 3.3 国产芯片：同时准备基金要求的交付

- 完成不少于 5 款芯片的调研，优先确认可用设备、软件版本和 profiling 能力。
- 确定用于交付的 2 款芯片，先在每个平台运行一个算子并取得性能报告。
- 确定不少于 5 个 Triton-TLE 算子及测试输入；优先选择两款芯片均支持、且能与规定的 FlagGems 版本比较的算子。
- 尽快记录立项时 FlagGems 版本及复现条件，不用之后任意选择的版本代替。
- 接入现有 profiler，并验证 analyzer 是否能帮助定位问题和选择修改方法。

**完成时应能拿出的东西**：设备与工具清单、可复现的初始测试结果、算子列表、第一批优化记录，以及对应任务书要求的交付进度。

### 3.4 随后扩展

- 在 XSAI 上推进更复杂的算子和 Triton/Triton-TLE 支持。
- 完成分段分析方法、优化知识库的实验。
- 在同一个 XSAI 配置上比较不同信息范围对优化的帮助。
- 根据结果整理哪些硬件信息值得提供给软件，以及哪些采集能力值得做成性能计数器。

### 工程任务：仓库与 XSAI 移植

负责人：待定。

- 建立仓库，按需要将自有或可纳入版本管理的 backend 作为 submodule。
- 对依赖外部安装的厂商工具，记录支持版本、安装条件和调用方式，不强行全部纳入 submodule。

跨平台部分先围绕采集和分析组织：

```text
XSAI：已有计数器 / ChiselDB / PerfCCT → XSAI-prof → XSAI-analyzer
国产卡：厂商 profiler → 已有分析工具 / 待补分析功能
NVIDIA：Nsight Compute → 已有分析功能 / 待补分析功能
                          ↓
       统一提供可用指标、代码位置、性能问题和支持判断的证据
                          ↓
                   Agent 选择优化动作
```

各平台不必提供完全相同的指标。统一表达数据含义、单位、来源、采集范围和缺失情况；缺失值不当作零。同名指标只有含义和测量范围一致时才直接比较。

## 5. 论文中三个平台分别回答什么问题

以下是实验组织建议，不预设论文结论或要求所有内容放入同一篇论文。

| 平台 | 主要回答的问题 | 应提供的证据 | 结论范围 |
| --- | --- | --- | --- |
| NVIDIA | 分段分析、analyzer 或动作选择方法，在已有工具条件下是否有效 | 相同硬件和任务下，与已有分析方式及 Agent 方法的比较 | 说明方法在 NVIDIA 上的效果，不据此声称掌握全部内部信息 |
| 两款国产芯片 | 方法能否用于其他软硬件环境，能否达到基金要求 | 同一平台优化前后的结果、工具适配情况、Triton-TLE 算子结果 | 区分可复用的方法和平台专用实现 |
| XSAI | 多提供哪些内部信息，会帮助 Agent 作出更好的修改 | 同一硬件配置下，控制 Agent 可见信息范围的对照实验 | 说明选定设计及算子上的信息价值，不直接推断所有芯片都相同 |

不能通过比较三种芯片的绝对速度来证明“白盒更好”。更合适的做法是在各自平台内比较优化效果，在 XSAI 内控制信息范围。

### 5.1 XSAI 上怎样比较信息的作用

建议分三组，其他设置尽量一致：

1. **只提供基本运行反馈**：任务、允许使用的软硬件接口、正确性结果和总性能。各组都保留编写合法程序所需的信息。
2. **增加约定的常规性能信息**：使用 XSAI 上已有且含义明确的计数器或汇总数据。逐项说明其与选定厂商 profiler 能力的对应关系，不宣称指标天然一一对应。
3. **增加内部分析信息**：按实际覆盖情况开放 ChiselDB / PerfCCT 数据及后续新增信息，并记录究竟新增了什么。

固定硬件配置、起始代码、输入、正确性要求、模型与优化流程；明确搜索预算，记录重复运行的变化。各组最终代码在相同测量设置下评估。

同时记录最终性能、尝试次数、模型使用量、采集与分析耗时、总用时和失败次数。既可在相同尝试次数下比较，也可在相同总用时下比较，但结果分开解释。

逐类增加或去掉信息，分析哪类信息改变了什么决策。不把“数据越多必然越好”作为预设；若 analyzer 同时给了更多优化建议，要另外区分信息增加和建议增加的影响。

实验应限制各组额外读取未授权的报告或 trace，但不声称可以清除模型此前已学到的硬件知识。

### 5.2 硬件参数与运行指标分开记录

- 硬件参数：例如缓存容量、执行单元配置，用来描述硬件设计。
- 运行指标：例如当前算子的计数器值、等待时间，用来描述本次执行。

在模拟器中改变硬件参数，研究的是“设计改变后性能怎样变化”；固定硬件、改变 Agent 可见的信息，研究的是“知道更多能否优化得更好”。两类实验单独设计，不混在一张加速图里。

任务书的 Top K 思路可先写为：离线筛选值得关注的硬件特征，再在具体运行中选出最值得分析的问题。Top-down 如何实现、各平台需要哪些指标，作为方法任务继续确定，不直接照搬某个平台的指标树。

## 6. 模拟器与仿真在这里做什么

是否需要周期精确，取决于要据此作出什么判断；工具名称本身不足以说明能力。

| 用途 | 需要的能力 | 结果如何使用 |
| --- | --- | --- |
| 检查程序计算结果、指令和接口使用 | 功能模拟或其他正确性检查 | 检查正确性，不用模拟器在主机上的运行时长代表目标芯片性能 |
| 检查执行顺序、数据访问或代码对应关系 | 能输出所需事件的 trace | 提出优化假设；trace 本身不保证准确反映延迟与竞争 |
| 比较候选实现的性能趋势 | 对相关延迟、带宽、资源竞争有建模且经过验证的性能模型 | 可用于初筛，最终使用目标平台测量或更可信的模型复核 |
| 分析细粒度流水线等待与竞争 | 覆盖目标问题的详细时序模型或 RTL 仿真 | 检查内部原因，并说明模型及外部存储系统的范围 |
| 研究硬件设计参数变化 | 可修改对应参数、且模型能反映其影响的模拟环境 | 支撑硬件设计研究，与固定硬件上的软件优化实验分开 |

XSAI 已有 RTL emu，应先利用现有能力。周期级结果是针对当前 RTL 与配套模型配置的结果，不直接等同于最终芯片实测性能。也需要区分目标硬件周期数与主机执行仿真的用时。

华为模拟器支线先回答：具体是什么工具和版本，输出哪些数据，时序或性能数字代表什么，怎样与真机或其他可信结果比较。若只有功能能力，可做功能检查和执行分析；若有性能模型，再评估能否用于选择优化方案。暂不预设其周期精度，也不要求为此重新开发一套模拟器。

公开的华为 msProf / msOpProf 文档已有算子仿真分析功能，包括指令流水图、代码热点和内存通道吞吐波形。若智源提供的是对应工具，可先研究如何把这些输出转成可供 Agent 使用的分析，并在真机上验证修改效果；这些文档本身不足以确认具体模拟器对目标硬件的周期精度。国产芯片并非完全无法获得细粒度信息，各平台实际可见的信息仍需逐项确认。
