案例 1：访存合并需要地址与事务证据

memory.coalesced_access · Excel 第 29 行

原规则待补的证据
Excel 用 L1 命中率低触发合并访存建议。流式连续访问也可能低命中，单个命中率不足以判断。
要观察什么
检查同一 warp 的地址分布、对齐及 stride；采集每次请求的 sectors/transactions、实际流量与有效数据量，并固定统计范围。
待检验的瓶颈假设
相邻线程读取不连续地址，产生额外内存事务，限制数据供给。
具体修改
保持算子语义和 dtype，调整线程到数据的映射或布局，让相邻线程优先读取连续地址。
怎样验证
同机对照原版和单项修改版；检查结果、事务/有效字节及未开启 profiler 时的时间。布局转换成本计入算子边界。
适用范围与反例
已有良好合并访问时通常无收益；不得用 L1 命中率或更高带宽单独判定成功。XSAI/国产卡需各自确认访问粒度。

案例 2：用流水级实验区分等待与资源压力

memory.multi_stage_pipeline · Excel 第 33 行

原规则待补的证据
Excel 以 long-scoreboard 阈值触发多级流水线。该等待也可能来自依赖链、缓存未命中等其他原因。
要观察什么
定位等待所在的加载/计算阶段，检查能否提前搬运、现有流水级数、异步指令，以及共享存储和寄存器余量。
待检验的瓶颈假设
迭代间可提前加载的数据仍串行搬运，计算阶段出现可隐藏的等待。
具体修改
固定 tile、dtype 和线程配置，在后端允许范围内比较 1/2/3 级流水；检查生成代码确实发生变化。
怎样验证
验证同步和数值结果；观察重叠、等待、资源占用和执行时间。出现资源压力导致回退时保留失败样本。
适用范围与反例
cp.async/TMA 是 NVIDIA 特定机制，不能直接用于 AMX/XSAI；国产卡需重新绑定搬运/同步接口。增加 stage 可能降低并行度。

案例 3：低 occupancy 是否真的需要缩小 tile

compute.register_tile_budget · Excel 第 27 行

原规则待补的证据
Excel 用 achieved occupancy 低给出建议；高性能 kernel 也可能有较低 occupancy，需要确认资源限制和关键路径。
要观察什么
结合编译器寄存器分配、spill load/store、局部内存流量、驻留限制和热点指令；不能把所有 local memory 都视为 spill。
待检验的瓶颈假设
累加 tile 或过度展开增加活跃值，导致寄存器溢出，额外流量影响关键路径。
具体修改
先减少单线程累加 tile 或展开程度，一次改一项；比较编译后的寄存器分配和 spill，避免仅强行限制寄存器数。
怎样验证
检查正确性和最终时间，同时报告 spill、复用和并行度变化。occupancy 提升而执行变慢也必须记录。
适用范围与反例
没有 spill 或性能已被其他资源限制时可能回退。XSAI 的编译器溢出与乱序核物理寄存器压力是不同现象，需分别观测。
