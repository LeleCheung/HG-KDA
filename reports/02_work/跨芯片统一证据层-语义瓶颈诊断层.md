我建议将“统一证据”更准确地称为：

> **标准化证据事实层**

它和“语义瓶颈诊断层”的根本区别是：

```text
标准化证据：硬件上观测到了什么？
语义瓶颈：这些观测共同说明性能为什么受限？
```

### 1. 标准化证据不只是统一名称

统一厂商指标名称只是第一步。这一层至少负责：

1. **统一概念**

   ```text
   XSAI: vec_active_cycles
   厂商A: vector_pipe_busy
   厂商B: cube_utilization
   ```

   如果测量含义确实相同或可以换算，才映射为：

   ```text
   compute.vector_active
   ```

2. **统一单位和分母**

   同样叫 utilization，分母可能分别是：

   ```text
   kernel 总周期
   device active 周期
   scheduler eligible 周期
   采样窗口
   ```

   这些指标不能直接当作相同字段。

3. **记录测量范围**

   ```text
   整个 Kernel
   某个计算簇
   某条流水线
   某个时间窗口
   ```

4. **保留来源和可追溯性**

   ```text
   canonical field: compute.vector_active
   raw field: vec_pipe_active_cycles
   platform: XSAI
   derivation: active_cycles / kernel_cycles
   ```

5. **处理缺失和不可比字段**

   国产卡没有某个 counter 时，应标记为 unavailable，不能用 0 代替。

所以标准化证据可以表示为：

```yaml
metric: compute.vector_active
value: 0.20
unit: ratio
denominator: kernel_elapsed_cycles
scope: kernel
source:
  platform: XSAI
  raw_metric: vec_pipe_active_cycles
availability: measured
```

### 2. 标准化证据是否应该输出百分比

**部分字段可以输出百分比，但这一层不应只输出百分比。**

它可以包含多种类型：

| 证据类型 | 示例 |
|---|---|
| 比例 | Vector active 20% |
| 相对硬件上限 | DRAM bandwidth 达到峰值的 82% |
| 原始计数 | 2.1M stall cycles |
| 资源数量 | 每线程使用128个寄存器 |
| 流量 | Spill traffic 320 MB |
| 时间 | Barrier wait 18 μs |
| 吞吐量 | 760 GB/s |
| 分布 | Load latency P50/P95 |
| 布尔状态 | 是否发生 spill |
| Trace关系 | DMA 与计算重叠区间 |

关键是：**每个百分比必须说明分母。**

例如：

```text
Vector active = 20%
```

必须继续说明：

```text
20% of kernel elapsed cycles
```

或者：

```text
20% of scheduler eligible cycles
```

这两者的意义完全不同。

### 3. “Vector computation unit underutilization 80%”属于哪一层

要分两种情况。

如果它只是：

```text
vector_inactive_ratio
= 1 - vector_active_ratio
= 80%
```

那么它仍然属于**标准化证据事实**，但建议命名为：

```text
vector_inactive_ratio = 80%
```

不要直接命名为 `underutilization`，因为“underutilization”容易让人误以为已经找到了瓶颈。

如果它表示：

> Vector 计算单元利用不足是当前 Kernel 的主要性能瓶颈。

这就属于**语义瓶颈诊断**。

仅凭 Vector active 20% 不能得出这个结论。例如：

```text
Vector active              20%
DRAM bandwidth utilization 95%
Memory dependency stall    63%
```

这更可能说明：

```text
Kernel 受内存系统限制
→ Vector 单元因为等待数据而空闲
```

此时 Vector 利用率低是**现象**，内存供数不足才是可能的**瓶颈原因**。

另一个算子可能是：

```text
Vector active              20%
DRAM bandwidth utilization 30%
Occupancy                  18%
Eligible workgroups        很少
```

这时更可能是：

```text
并行度不足
→ 无法产生足够的可执行工作
→ Vector 单元利用率低
```

同一个 `vector_active=20%`，可以对应完全不同的优化动作：

| 真正原因 | 候选动作 |
|---|---|
| 内存延迟、数据供给不足 | 预取、double buffer、增加 pipeline stage |
| 并行度不足 | 调整 tile、block size、任务划分 |
| 寄存器压力限制 occupancy | 缩小 register tile、减少 unroll |
| 指令依赖链过长 | 软件流水、重新安排指令 |
| 同步等待 | 减少 barrier、重构生产者消费者关系 |
| 算子规模太小 | fusion、batching、减少 launch 开销 |

这正是语义瓶颈层存在的原因。

### 4. 语义瓶颈层应该输出什么

建议输出：

```yaml
bottleneck: compute_underutilization
subtype: insufficient_parallelism
severity: high
confidence: 0.78

supporting_evidence:
  - compute.vector_active = 0.20
  - execution.occupancy = 0.18
  - scheduler.eligible_work = low

contradicting_evidence:
  - memory.bandwidth_utilization = 0.35

alternative_hypothesis:
  - memory_latency_starvation
```

其中有三个不同的数，不能混用：

| 数值 | 含义 |
|---|---|
| `vector_active=20%` | 硬件测量比例 |
| `severity=high/0.8` | 瓶颈严重程度 |
| `confidence=0.78` | 系统对该诊断的可信程度 |

`severity=0.8` 不能解释为“该瓶颈占用了80%的执行时间”。计算、访存和同步经常重叠，多个瓶颈分数也不要求相加为100%。

因此，这三层最准确的关系是：

```text
平台原始字段
    ↓ 字段映射、单位换算、分母和来源记录
标准化证据事实
    例如 vector_active=20%、occupancy=18%
    ↓ 多证据联合推断 + 静态硬件知识
语义瓶颈诊断
    例如“并行度不足导致计算流水线供给不足”
    ↓ 匹配触发条件、适用前提和风险
结构化候选动作
    例如调整 tile/block，增加可执行 workgroup
```

所以你的理解“统一各芯片厂商名称”是对的，但还需要补上**单位、分母、测量范围、来源、缺失状态和可比性**。这一层输出的是带测量定义的事实，其中一部分是百分比；下一层才判断这些事实是否构成瓶颈，以及瓶颈的原因是什么。
