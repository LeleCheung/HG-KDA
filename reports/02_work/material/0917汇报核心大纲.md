# HG-KDA：从 Profiling 证据到算子优化动作

## 0. 本次汇报要讲清楚的结论

现有 Kernel Agent 已经具备“生成或修改代码—编译—运行—评测”的迭代闭环，但 Profiling 信息如何支持瓶颈判断、瓶颈如何导出优化动作，通常隐含在 Agent 的模型知识和上下文推理中。

HG-KDA 将这段推理显式化：

```text
厂商原始 Profiling 数据
→ 跨平台标准化证据
→ 细粒度瓶颈诊断
→ 带适用条件的候选动作
→ Agent 修改 Kernel / IR
→ 正确性、性能和证据变化验证
```

本项目的核心研究问题是：

> 在硬件可观测字段不完整且跨芯片不一致的条件下，如何把运行证据转换为可信、可验证、可迁移的算子优化动作？

## 1. 四个核心问题

| 核心问题 | 需要得到的结果 | 主要解决方法 |
| --- | --- | --- |
| 测到了什么？ | 有明确单位、分母、作用域和来源的原始观测 | XSAI-emu、国产芯片 Profiler 调研与适配器 |
| 如何跨平台表示？ | 保留平台差异和缺失状态的标准化证据 | 跨平台 Schema、字段映射、microbenchmark 校准 |
| 为什么性能受限？ | 带原因、严重度、置信度和支持证据的瓶颈诊断 | Top-down、问题条件化 Top-K、XSAI 干预验证 |
| 下一步可以做什么？ | 带前提、风险、预期效果和验证方法的候选动作 | 动作映射、FlagGems 历史版本、动作收益模型 |

### 1.1 测到了什么？

这一层保存硬件和工具实际产生的观测：

```text
运行时间与吞吐量
计算单元活动率
访存流量、带宽与 replay
寄存器使用与 spill
并行度与 occupancy
同步与等待
编译配置、错误和生成代码
```

每个数值都需要携带测量定义。例如 `vector_active=20%` 还必须说明分母是 Kernel 总周期、设备活动周期还是某个采样窗口。

XSAI-emu 提供更完整的白盒观测；国产芯片 Profiler 调研确定目标平台真正可用的字段、导出方式、稳定性和厂商已有诊断能力。

### 1.2 如何跨平台表示？

建立跨平台标准化证据 Schema，并同时保留原始字段：

```text
raw metric + platform + unit + denominator + scope
→ canonical semantic metric + mapping type + availability
```

字段映射分为四类：

| 映射类型 | 含义 |
| --- | --- |
| `direct` | 指标定义一致，可以直接对应 |
| `derived` | 由多个原始字段计算得到 |
| `proxy` | 只能作为目标语义的近似观测 |
| `unavailable` | 当前平台无法观测，保留缺失标记 |

这一层的目标是形成可追溯的证据事实。例如：

```text
compute.vector_activity = 0.20
execution.occupancy = 0.18
memory.spill_traffic = unavailable
```

标准化不意味着不同芯片完全等价。原始值、换算方法、平台来源和缺失状态必须保留。

### 1.3 为什么性能受限？

Top-down 提供分层诊断框架：

```text
端到端开销
├── Host / Launch
└── Device Execution
    ├── Compute
    ├── Data Movement
    └── Synchronization
        ↓
寄存器压力 / 并行度不足 / 带宽饱和 / 访存延迟 / 同步失衡
```

问题条件化 Top-K 为当前诊断节点选择最有区分力的证据：

```text
Top-down：当前应该问什么问题？
Top-K：回答这个问题需要看哪些证据？
```

例如，区分“寄存器压力”和“并行度不足”时，优先查看寄存器使用、spill、occupancy、active workgroups 和 eligible work；区分“访存延迟”和“带宽饱和”时，优先查看带宽利用率、memory wait、cache 命中、replay 和 outstanding requests。

最终输出应是诊断假设，而不是单个 counter 的改名：

```yaml
bottleneck: compute_underutilization
cause: register_pressure
severity: high
confidence: 0.82
supporting_evidence:
  - register usage 接近上限
  - occupancy 低
  - spill 存在
alternative_hypothesis:
  - insufficient_parallelism
```

### 1.4 下一步可以做什么？

动作映射为每类瓶颈提供带条件的候选动作：

```yaml
bottleneck: register_pressure
action: reduce_register_tile
preconditions:
  - register pressure 高
  - occupancy 低
expected_effects:
  - register usage 下降
  - spill 减少
  - occupancy 提高
risks:
  - 数据复用降低
validation:
  - correctness 通过
  - latency 下降
  - 相关证据按预期变化
```

动作知识的构建路径是：

```text
大模型与专家经验 → 候选先验
FlagGems 父子版本 → 真实修改与收益样本
XSAI 受控实验 → 动作机制和证据变化验证
国产卡真机 → 目标平台收益与风险校准
```

## 2. 各条工作线分别解决什么

| 工作线 | 主要解决的问题 | 直接产出 | 不负责单独解决的问题 |
| --- | --- | --- | --- |
| 国产芯片 Profiler 调研 | 目标芯片能看到什么 | 工具和字段能力矩阵、原始 Profile、平台 Adapter | 无法仅凭字段列表完成瓶颈诊断 |
| Top-down | 按什么层次缩小瓶颈范围 | 瓶颈分类树、诊断路径、停止条件 | 不直接决定具体优化动作 |
| 问题条件化 Top-K | 当前问题需要哪些证据 | 每个诊断节点或动作对应的最小证据集合 | 不证明字段与收益之间的因果关系 |
| XSAI-emu | 证据—瓶颈—动作关系是否成立 | 完整观测、受控变体、机制标签、动作前后证据 | 不直接保证结论能迁移到国产卡 |
| 迁移学习 | 白盒知识如何低成本迁移到灰盒芯片 | 语义层迁移、目标平台少样本校准、退化曲线 | 不应直接搬运原始字段名和固定阈值 |
| 动作映射与 FlagGems 版本 | 判断瓶颈后尝试什么 | 条件化动作规则、真实版本转换样本、收益标签 | 初始大模型生成规则不能直接视为事实 |

### 2.1 国产芯片 Profiler 调研

调研重点不是罗列工具名称，而是建立目标平台的可观测边界：

```text
字段名称、定义、单位、分母和作用域
导出格式与自动化接口
单 Kernel 定位能力
字段稳定性与采样限制
厂商已有 Roofline、Advisor 和优化建议
```

交付物应包括：平台能力矩阵、一个最小可复跑算子的原始 Profile、字段说明、厂商诊断及对应候选动作。

### 2.2 Top-down 与 Top-K

二者应组合使用：

```text
Top-down 选择诊断节点
→ Top-K 选择该节点所需证据
→ 证据不足时追加测量
→ 输出细粒度瓶颈及备选假设
```

Top-K 的核心是决策相关性。即使测量预算充足，把几百个相关、重复且平台相关的 counter 全部交给 Agent，仍然难以形成稳定动作。

XGBoost 可以预测瓶颈类别、动作成功率或动作收益；SHAP 用于发现候选字段及其交互。SHAP 反映预测重要性，因果方向需要 XSAI 干预或真机动作实验确认。

### 2.3 XSAI-emu

XSAI-emu 的主要作用是建立高质量源域数据：

```text
构造 tile、layout、pipeline、循环顺序等受控变体
→ 采集完整 counter、trace、时延和资源数据
→ 比较动作前后的状态变化
→ 形成 (状态 s，动作 a，下一状态 s'，收益 r) 样本
```

它能够支持三类标签：

1. 哪些证据对应某类瓶颈；
2. 某个动作是否缓解该瓶颈；
3. 哪些字段被屏蔽后，诊断和动作选择开始退化。

### 2.4 迁移学习

从 XSAI 迁移到国产卡的对象包括：

```text
统一语义 Schema
瓶颈分类体系
问题条件化候选证据
瓶颈—动作知识
源域诊断模型和动作收益模型
```

目标国产卡需要重新学习或校准：

```text
厂商原始字段到语义证据的映射
平台特定阈值
动作参数
动作收益和失败风险
```

可采用“源模型/规则 + 目标平台少量样本校准”的第一版实现。实验比较目标样本量为 `0 / 5 / 20 / 50` 时，从零训练、直接迁移、语义迁移加校准等方法的瓶颈判断和动作选择效果。

## 3. 离线建模与在线优化闭环

### 3.1 离线：XSAI 建模与经验沉淀

```text
XSAI 受控 Kernel 变体
→ 完整 Profiling 和正确性/性能测量
→ 标准化证据与瓶颈标签
→ 动作前后转换样本 (s, a, s', r)
→ 经验数据库
→ 瓶颈模型、Top-K 证据索引、动作收益模型
```

经验数据库至少保存：

```text
硬件、算子、shape、dtype、编译配置
原始字段、标准化字段、字段来源和缺失状态
父子版本、代码 diff、动作类型
修改前后正确性、性能和 Profiling
诊断、置信度、动作前提、风险和验证结果
```

### 3.2 在线：国产卡诊断与优化

```text
国产卡 Profiler
→ 平台 Adapter
→ 标准化证据
→ Top-down 选择诊断节点
→ 条件化 Top-K 选择证据
→ 瓶颈诊断
→ 候选动作排序
→ Agent 修改 Kernel / IR
→ 真机验证
→ 新样本回写数据库
```

## 4. 当前已有进展及证据边界

### 4.1 动作映射

- 已导出 78 条动作和 3 个演示案例；
- 当前均属于 `llm_prior_unvalidated`，阈值、后端能力和加速声明仍需实验验证；
- 下一步需要 FlagGems 可重跑父子版本、代码 diff、前后 Profile、正确性和失败记录。

### 4.2 XSAI-emu 最小闭环

- 已在预编译 XSAI-emu 上运行 Hello 和 GEMM 算子族；
- 已隔离 GEMM guest instruction 窗口并采集 RTL counter 与 ChiselDB 数据；
- 在 N=16 整数 GEMM 微案例中，已验证两条 `intervention_supported` 映射：
  - replay/访问压力 → 循环换序；
  - 冗余 load/指令 → 寄存器分块；
- `reg4x4` 已出现资源压力但仍快于 `reg2x2`，说明动作边界需要相邻配置实测，不能仅凭压力指标判断优化方向；
- 当前结果仅覆盖单一微案例和通用 RISC-V 路径，不能外推到矩阵扩展或国产 AI 芯片。

### 4.3 Agent 动作选择 Pilot

- 已建立 `latency-only`、`raw counters`、`semantic mapping` 三种输入条件的盲化评测流程；
- 两个 held-out case 中，前两种输入均为 `1/2`，结构化语义映射为 `2/2`；
- 当前样本量只有两个，该结果只证明评测链路可运行，不能作为统计性优越结论；
- 下一步需要扩展 shape、循环排列、tile 回退点和重复采样。

### 4.4 国产芯片

- 当前只完成官方工具入口和公开能力预研；
- 尚未在真机上执行 Profiler；
- 拿到机器后的第一目标是跑通一个最小算子，保存完整环境、原始 Profile、厂商建议、候选动作、正确性和无 Profiler 的基线时间。

## 5. 需要验证的研究假设

### H1：显式语义接口提高动作选择质量

比较：

```text
latency-only
raw counters
固定全局 Top-K
问题条件化 Top-K
语义瓶颈
语义瓶颈 + 结构化动作映射
```

指标：动作命中率、正确性通过率、有效修改比例、Speedup、回退率、测量次数。

### H2：Top-down 与条件化 Top-K 提高诊断效率

比较全量 counter、固定 Top-K 和分层条件化证据选择，考察瓶颈分类准确率、置信度校准、追加测量次数以及新 shape 上的泛化。

### H3：XSAI 白盒知识降低国产卡标注需求

比较国产卡从零学习、XSAI 模型直接迁移、语义层迁移加少量国产卡校准，绘制目标样本量与诊断/动作性能之间的曲线。

### H4：证据变化可以验证动作机制

动作成功除了要求正确性和时延改善，还应检查相关证据是否按预期变化。这样可以区分“动作碰巧变快”和“动作确实缓解了所诊断的瓶颈”。

## 6. 明日汇报建议页序

### 第1页：现有 Kernel Agent 的缺口

用 A/B 对照图说明：传统 Agent 的 Profiling 到动作推理隐含在模型内部；HG-KDA 把它拆成标准化证据、瓶颈诊断和候选动作三个显式接口。

### 第2页：四个核心问题与方法分工

展示：

```text
测到了什么？
→ 如何跨平台表示？
→ 为什么性能受限？
→ 下一步可以做什么？
```

在四个问题下标注国产卡 Profiler、Top-down、Top-K、XSAI-emu、动作映射和迁移学习的职责。

### 第3页：XSAI 白盒最小闭环

展示 GEMM 受控变体、两条已支持映射，以及 `reg4x4` 边界案例。重点说明 XSAI 的价值是产生完整证据和验证动作机制。

### 第4页：Agent 动作选择 Pilot

展示三种输入条件、两个 held-out case 和当前结果，同时明确样本量限制。该页证明评测框架已经建立。

### 第5页：国产卡灰盒调研与迁移计划

展示目标平台能力矩阵、字段 Adapter、少样本校准和白盒到灰盒迁移实验设计。

### 第6页：下一阶段交付

1. 在国产卡上跑通一个可复现的 Profiler 最小案例；
2. 扩大 XSAI GEMM 的 shape 和 tile 范围，找到动作回退点；
3. 向智源申请 20–50 对可重跑 FlagGems 父子版本；
4. 扩展动作选择评测，比较 latency、raw counter、Top-K、语义诊断和动作映射；
5. 固化跨平台 Schema 和第一版平台 Adapter。

## 7. 汇报时的核心表述

> 国产卡 Profiler 确定目标平台的可观测边界，Top-down 组织诊断路径，问题条件化 Top-K 选择当前决策所需的证据，XSAI-emu 通过白盒干预建立并验证证据—瓶颈—动作关系，动作映射和 FlagGems 版本提供候选动作及真实收益样本，迁移学习再用少量国产卡数据完成字段、阈值和收益校准。

> HG-KDA 的目标是将这条原本隐含在 Agent 内部的推理通路，变成可检查、可训练、可迁移并能通过真机实验验证的系统接口。
