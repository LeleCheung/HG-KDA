# 第二次研究院汇报准备：从硬件信息到优化动作

本文件用于第二次智源汇报准备。第一次汇报材料见 [01_work](../01_work/)，本次动作映射进展见 [PPT](profiling信息到优化方法的映射机制.pptx)。

## 1. 对上次 PPT 的重新判断

上次汇报把系统画成 Static Hardware KB、Dynamic Profiler、Evidence Fusion、Bottleneck Diagnosis、Kernel Action Plan 和 Evidence Memory。这个图的方向是对的，但模块较多，容易让听众以为项目是在同时开发一个知识库、一个 profiler、一个诊断系统和一个 Agent 平台。

更清楚的说法是，项目有三个核心模块：

```text
静态硬件知识库
      +
动态 profiler
      -> 证据到优化动作的映射
      -> Agent 搜索、验证和记忆
```

其中最后的 Agent、Harness 和 Evidence Memory 是承载闭环的系统底座；真正需要研究的是三种信息如何共同决定下一步优化动作。

上次 PPT 中的 M1--M6 信息级别、Top-K Counter Index、分层 Roofline、动作注册表和 Evidence Memory 都可以保留，但应作为这三个模块内部的机制，而不是继续增加新的一级模块。

## 2. XSAI 和国产芯片各自做什么

### 2.1 XSAI 不是简单的“profiling 信息全集”

XSAI 的价值在于：硬件、编译器和运行环境可控，可以获得接近完整的静态和动态证据，包括 RTL/emu counter、流水级时间戳、指令和 uop 流、load replay、存储系统事件、编译产物以及机器码。它适合回答“如果知道完整硬件行为，哪些证据能够解释性能，哪些证据会触发哪种优化”。

但 XSAI 的 emu/RTL 结果不等于真实芯片上的最终性能。它可能有仿真开销、模型误差和与实物不同的时序。因此汇报时应称为“高可观测、可干预的白盒研究平台”，把它用于机制研究、训练数据构造和方法验证，不要把它说成所有 profiling 信息的绝对真值。

### 2.2 国产卡是灰盒验证平台

国产卡的作用不是简单地“再跑一遍五个算子”，而是测试方法在真实生态中的信息边界：能拿到哪些 profiler 字段，字段是否稳定，完整 profiling 要付出多少轮测量，厂商编译器会暴露哪些资源信息，以及缺失硬件细节后 Agent 的性能损失有多大。

可以把国产卡定义为灰盒条件：公开文档、编译日志、kernel 时间、资源使用、少量 counters 和厂商 profiler 导出结果可见；内部微架构、完整事件定义和编译器启发式不可见。若某张卡能开放更多字段，就在实验中明确标注可观测性等级，而不要强行归类为全黑盒或全白盒。

### 2.3 两个平台形成互补的实验逻辑

```text
XSAI：完整观察 + 主动干预
  -> 找到瓶颈机制、验证特征因果性、构造训练/校准数据

国产卡：部分观察 + 真实部署
  -> 测试最小必要特征、工具适配、预算和跨平台迁移
```

这比“XSAI 做 profiler，国产卡做应用”更有研究含义。XSAI 提供可解释性和上限，国产卡提供真实性和泛化压力。

## 3. 国产芯片 profiler 调研的具体问题

到智源拿到服务器后，第一步应建立每个平台的 profiler 能力矩阵。不要先问“有没有 Top-down”，而要逐项记录：

| 类别 | 需要确认的内容 |
|---|---|
| 调用与时间 | kernel/API 时间、并发、launch gap、同步等待、重复测量方差 |
| 计算资源 | vector/matrix/tensor 单元利用率、指令数量、吞吐率、空闲周期 |
| 内存系统 | HBM/DDR 带宽、片上 SRAM/cache 命中、DMA 次数和等待、访存合并 |
| 调度执行 | occupancy/活跃线程或 task、流水线 stall、负载不均衡、barrier 等待 |
| 编译反馈 | register/local memory、片上存储占用、spill、向量化/矩阵化、编译告警 |
| 追踪格式 | GUI 还是 CSV/JSON，是否支持脚本导出，字段定义和版本是否稳定 |
| 干预能力 | 能否改变 tile、线程、layout、pipeline、融合和数据类型并重新测量 |

公开资料中可优先查看的工具入口包括 Huawei Ascend 的 MindStudio/msprof、Cambricon MLU 的 BANG/CNPerf 相关工具、MUSA/摩尔线程的 profiler，以及海光、沐曦、燧原等厂商随 SDK 提供的性能分析工具。具体名称、事件数量和导出格式必须以现场 SDK 版本为准，不能把 NVIDIA Nsight 的指标名称直接映射过去。

最终需要产出一个 adapter：把各家 profiler 的原始 CSV/JSON/trace 统一成项目 schema，并记录 `device`、`driver`、`tool_version`、`event_definition`、`sampling_cost` 和 `confidence`。没有统一 schema，就无法比较 XSAI 和国产卡，也无法让 Agent 使用历史证据。

## 4. 动态 profiler 的研究重点

上次 PPT 已经提出了离线 Top-K Index，这是一个很好的起点，但需要把它讲成“面向诊断和动作选择的语义证据索引”。预算只属于在线 profiler 的附加问题：决定何时追加昂贵指标、做多少次重复测量，以及何时停止；它不是 Top-K 的核心价值。

离线阶段：用同一个算子语义，通过 tile、线程、layout、pipeline、融合和数据类型等简单变体制造不同机器码；运行完整 profiler，记录静态特征、编译特征、运行 counters 和真实性能；用 Roofline/层次诊断与 XGBoost/TreeSHAP 共同筛选候选特征，并把它们压缩成能够区分瓶颈和优化动作的语义证据。

在线阶段：根据算子、shape、dtype、硬件型号和已有历史，查询当前决策对应的证据索引。每次测量都要输出瓶颈类别、置信度、证据字段和下一步可选动作；只有证据不足时，才追加更昂贵的 counters。这样 Dynamic Profiler 才是一个语义证据模块，预算控制是它的附加策略，而不是核心定义。

## 5. 本科生“映射机制”进展应怎样理解

当前进展已经有了一个可展示的雏形：动作注册表包含 axis、最小 SM、所需硬件特征、触发证据和 good/bad/direction 条件；已有 compute、memory、latency 三类共 78 个优化方法。这说明团队开始把“经验”变成结构化对象，这是重要进展。

但注册表现在更像专家知识目录，还不能直接称为映射机制。下一步需要补上四件事：

1. **证据定义**：每个 `trigger_evidence` 必须对应具体 profiler 字段、单位、归一化方式和采集成本；
2. **动作定义**：动作要落到 Triton/IR/pass/调度参数，例如 tile、layout、vectorization、double buffer、fusion 或线程映射；
3. **触发验证**：记录触发前后的真实性能、瓶颈变化和正确性结果，区分相关性与因果性；
4. **适用范围**：写明算子族、shape bucket、dtype、硬件型号和失败条件，避免一个规则被误用于所有算子。

建议把注册表字段改成类似下面的形式：

```json
{
  "action": "double_buffer",
  "bottleneck": "memory_wait",
  "scope": {"op": "gemm", "dtype": "bf16", "shape": "large_k"},
  "required_features": ["dma_overlap", "onchip_capacity"],
  "trigger": {"dram_stall_ratio": ">0.35", "compute_util": "<0.60"},
  "expected_effect": ["increase_overlap", "reduce_wait"],
  "risk": ["more_storage", "lower_occupancy"],
  "validation": ["correctness", "latency", "memory_peak"]
}
```

## 6. 下一次汇报建议

建议主题改为：**“从 Profiling 证据到算子优化动作：XSAI 白盒研究与国产卡灰盒验证”**。静态知识库压缩为一页背景，主体放在剩下两个模块和两者之间的闭环。

推荐 8 页：

1. **问题重述**：相同算子在不同芯片上的性能差异，Agent 需要的是下一步动作，不是更多原始 counter；
2. **三模块总图**：静态先验、动态证据、证据到动作；标出 Agent/Harness 是底座；
3. **XSAI 白盒路径**：kernel 变体、编译、RTL emu、counter/uop/波形、性能结果；强调可干预和可解释；
4. **国产卡灰盒路径**：实际可获得的 profiler、编译日志和时间信息；展示一张能力矩阵；
5. **Dynamic Profiler**：离线完整采集、语义证据索引、在线按诊断问题查询；
6. **本科生进展**：78 个动作注册表，展示一个从证据到动作的完整案例；
7. **验证计划**：latency-only、raw counter、诊断、诊断+映射、主动 profiling 的消融；XSAI 与两款国产卡的角色；
8. **近期任务和需要智源支持的事项**：申请服务器和 SDK 权限、确认 profiler 导出、选择首批算子、建立共同 benchmark。

## 7. 一个适合现场讲的案例

不要只展示“采集了多少 counter”或“注册了多少优化方法”。选一个算子和一个动作完整走通：

```text
算子/shape
 -> profiler 发现 memory wait 高、compute utilization 低
 -> 诊断为数据供给瓶颈
 -> 匹配 double buffer + layout/tile action
 -> 编译和 correctness
 -> 性能改善及瓶颈变化
 -> 记录规则适用范围和失败条件
```

XSAI 上展示完整 counter 和干预前后变化；国产卡上展示只能拿到的字段，以及少一个字段时规则是否仍能工作。这样听众能直接看到项目的研究问题，而不是看到三个并列的软件模块。

## 8. 汇报时需要避免的表述

- 不要说 XSAI 是“所有 profiling 信息的全集”；应说高可观测白盒研究平台。
- 不要说国产卡只是“灰盒复现”；它负责验证最小信息集合、真实工具成本和迁移能力。
- 不要把 Top-K 特征重要性直接说成因果关系；需要干预实验。
- 不要把 78 个优化方法直接说成已经完成映射；目前是结构化动作库和规则原型。
- 不要把 profiler、诊断和动作计划画成互不相干的组件；它们应表现为一次闭环中的不同阶段。

下一次汇报的核心信息可以压缩成一句话：

> XSAI 帮我们弄清楚哪些硬件证据真正解释性能，国产卡帮我们验证在只能看到部分证据时，最小的信息集合能否仍然指导 Agent 做出正确的优化动作。
